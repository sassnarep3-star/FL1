F01 2017 NFL Personnel (Injury) Report Policy PDF

Unreachable source Severity Medium

The policy document that every secondary source cites for injury-designation definitions returned HTTP 404 ('FLAG ON THE PLAY') from operations.nfl.com on 2026-11-14. Consequently this site does not quote the policy text and does not assert what 'Questionable' or 'Doubtful' officially mean. Only the categories observed on the live report are recorded.

Sources consulted: S12

What was done instead. No definition text published. Category labels reproduced exactly as observed.

F07 One Week 10 game was already final at capture time

Method hazard Severity Medium

Washington at New York Giants kicked off Thursday 2026-11-12 and finished 24-21. Their injury tables are still shown in the Week 10 report. Using those rows as a pre-game signal would be look-ahead bias. They are the completed game's report, not a forecast input.

Sources consulted: S01 S04

What was done instead. Flagged so no analysis treats the completed game's rows as forward-looking.

Sources consulted: S01

What was done instead. Deficiency magnitude left blank. See question Q05 and suggestion SG04.

F11 Player-name collisions make name joins unsafe

Data hazard Severity Medium

Two different players named Marcus Harris appear in the captured data: a Tennessee cornerback and a Kansas City defensive tackle. NFL player URLs disambiguate them with numeric suffixes, but plain names do not. Any join performed on player name alone will silently merge distinct people.

Sources consulted: S01

What was done instead. Rows kept separate. Any future join must key on the player URL, not the display name.

F15 A parallel session's injury CSV had a column-shift bug on multi-injury cells

Cross-check finding Severity Low

A concurrent session independently transcribed the same Week 10 report into data/injuries.csv. Comparing the two transcriptions row by row: all 161 rows it contains also appear in this repo's 345-row capture, with no row present only in theirs. 156 of 161 rows match field for field, which is a useful independent confirmation of the capture. The 5 that differed all involve a player with two listed body parts: 'Ankle, Knee', 'Wrist, Chest', 'Knee, Achilles', 'Ankle, Triceps' and 'Ankle, Knee'. Because that CSV was comma-delimited and the injury field was unquoted, the second body part shifted into the adjacent columns, so the practice and game status fields were displaced. This repo's capture preserves the full published value and the correct game status, and the raw page capture confirms it (e.g. A.J. Brown 'Ankle, Knee / Limited Participation / Questionable').

Sources consulted: S01

What was done instead. This repo keeps its own capture, which was verified line by line against the raw page. The other session's files are preserved in archive/v2/ for reference. Any future CSV export must quote every field containing a comma.

F16 Houston Texans depth chart published as an image

Source not machine-readable Severity Medium

https://www.houstontexans.com/team/depth-chart loads, but the chart itself is rendered as an image inside a photo-gallery widget rather than as a position table. No player names are machine-readable. Houston is therefore the only club of 32 with no depth chart on this site. The Texans roster page does publish a readable table, but it is ordered alphabetically, not by depth, so it cannot be substituted without inventing the string ordering. Depth is an ordering, and the ordering is the fact being reported.

Sources consulted: S01 S49

What was done instead. Houston is absent from the Backup Depth page and counted as uncovered. Nothing inferred in its place.

F17 Player-prop correlations are computed estimates from a third-party mirror

Data provenance Severity Medium

data/prop-correlations-d.csv coefficients are computed from nflverse player_stats 1999-2024 via the Beexly/Sports mirror (file commit 2026-11-07), QA-gated (schema, coverage, 100% score join vs games.csv, distribution sanity, deterministic rebuild). They are model inputs, NOT official NFL statistics, and must not be presented as verified league facts. The source parquet is not committed and its prior workspace-only path is absent from this checkout; therefore the prop-correlation rebuild check V9 is BLOCKED here. The existing coefficients remain third-party-derived and were not independently regenerated in this run.

Sources consulted: S47 S48

What was done instead. Retain the third-party label; for reproducible refreshes, fetch a pinned source artifact and record its content hash. Until that input and QA run are available, treat V9 as BLOCKED and do not claim this checkout independently reproduced the estimates.
